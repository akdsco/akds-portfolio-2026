# skills layout

- Date: 2026-07-16 15:34
- Branch: skills-layout

## Problem / Context

The Skills section (`components/landing/skills.tsx`) renders `skills` from
`data/portfolio.ts` into a `sm:grid-cols-2` grid, in data order. Every CSS grid
row is as tall as its tallest cell, so pairing a short category with a tall one
carves a hole beside the short one. The worst offender was row 1: Languages (4
items) beside Frontend (14).

Measured in-browser at 1440px wide — content height per category, and the waste
each row creates:

| Row | Pair                        | Heights   | Waste |
| --- | --------------------------- | --------- | ----- |
| 1   | Languages \| Frontend       | 100 / 193 | 93px  |
| 2   | Backend \| AI / LLM         | 131 / 193 | 62px  |
| 3   | Databases \| Infrastructure | 179 / 193 | 14px  |
| 4   | Testing \| Observability    | 211 / 148 | 63px  |
| 5   | Practices \| Integrations   | 242 / 162 | 80px  |

312px of dead space in a 1128px grid. Note there are **ten** categories, not the
six visible in a first screenshot — the section sits inside the collapsed
`AboutMore` panel, so any pairing decision has to account for all ten.

## Plan

Reorder the `skills` array so each row pairs categories of similar bulk *and*
related meaning. AI / LLM and Frontend are both exactly 193px, which makes them
a free perfect row — and matches what the owner suggested.

Target order, and the narrative it reads as:

1. AI / LLM | Frontend — what gets built (and the headline positioning)
2. Languages | Backend — core engineering
3. Databases & Data | Infrastructure & DevOps — platform
4. Testing & Quality | Practices & patterns — how it's built
5. Observability & Product Analytics | Integrations shipped against — production surface

This is also the mathematical optimum: pairing the ten measured heights to
minimise total waste gives 90px, and this ordering hits exactly that. Semantics
and layout agree, so there's no trade-off to arbitrate.

Rejected: CSS `columns-2` (masonry-style flow) would drive waste to ~0 at every
width automatically and self-maintain as skills are added. Not chosen because the
browser picks the column split, so "these two categories sit side by side" stops
being controllable — and the pairing carries meaning here. Worth revisiting if the
category count grows enough that hand-tuned order becomes a chore.

## Increments (test-first)

Layout balance has no unit surface — jsdom has no layout engine, so a Vitest
assertion about column heights would be fiction. The honest harness is
measurement in a real browser, run before and after:

1. verify (red): measure each category's content height and per-row waste at
   1024/1280/1440/1600/1920 in the current order → 312px waste @1440.
2. impl: reorder the `skills` array mechanically, so no item can be altered by
   hand; prove the diff is a pure permutation by comparing sorted line sets.
3. verify (green): re-measure at the same five widths. Waste must drop at every
   width, with no width regressing.

## Notes

- Result: waste 312→90px @1024, 311→125 @1280, 218→32 @1440, 218→94 @1600,
  187→63 @1920. Section 63–111px shorter depending on width. No width regressed.
- The order is load-bearing but looks arbitrary in source, so it carries a
  comment. Adding or renaming a category re-opens the gaps — re-measure.
- Content untouched: verified the reorder is a pure permutation of lines.
